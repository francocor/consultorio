## Findings

1. **The psychologist can read Valentina's prescriptions, and that is correct.** The probe assumed the psychologist does not treat her. The agenda of the demo gives every adult to both the cardiologist and the psychologist (`schedule.ts`: `pools.cardiology` and `pools.psychology` take the same adults), and a care relationship follows an appointment. So the psychologist treats Valentina in the seed, and the rule of the spec (the prescriber and the professionals who treat the patient) lets her read. The probe now reads `care_relationship` and asserts per professional; the pediatrician (never treats an adult), reception, the administration and the owner get nothing. No code was wrong; the test's assumption was.
2. **`stage3-booking` "a visitor books ... and the patient cancels from the link" fails when the clock is early on a weekday.** It books the first free time of the psychologist (Mondays to Thursdays from 15:00), and when the run is at 08:45 on a Monday that time is inside the deadline to change online (`rescheduleDeadlineHours`), so `canChange` is false and the page has no "Cancelar el turno". It failed alone as well as in the full run. It does not touch anything of this unit (public booking, the agenda); I did not re-run it on the integration tip. Not fixed here (a Stage 3 spec).
3. **`stage4-demo` "closes the register"** fails with the layout check on the charges to invoice (a page wider than the screen), as in Stage 5 integration 1: it is fixed on the Stage 4 fix branch and passes once that branch is merged.
4. **The seed reads a clinical table as the system.** `listPrescriptionsForPatient` reads `prescription` as `SYSTEM_USER_ID` (the module does it by design), and so does the reset to list the PDFs. The snapshot and the tests read prescriptions and signatures as each professional, which is the strict way.
5. **`CREATE OR REPLACE FUNCTION` replaces the `SET` options of the function.** The first version of 0590 repeated `SET search_path = pg_catalog, public` from 0018 and lost the `pg_temp` pin that 0022 had added to every definer function; `definer-functions.test.ts` failed in the full integration run (the targeted runs before it did not include that file). Fixed in `9aef93b`, with the reason in the migration.

## Deviations from the tasks and the design

1. **"Demo email never reaches SMTP" is exact in production and, outside production, the development catcher still receives a copy.** The browser suites of Stages 1 to 5 read the demo organizations' emails (invitations, reset links, booking codes, portal notices) from Mailpit; the configured SMTP server outside production is that catcher, by the Stage 1 decision. Taking it away would have rewritten about twenty specs. In production nothing is forwarded, and the test proves it with an SMTP sender that records.
2. **In production the outbox exists only where the provider console is on.** The console is where it is read and it is already guarded (`LOCAL_PROVIDERS_CONSOLE` needs `ALLOW_LOCAL_PROVIDERS` in production). Without the console a production demo keeps the throwaway in-memory sender it had, so the table does not grow where nobody can read it.
3. **`app.demo_reset` was replaced in migration 0590.** The task says "removed by `demo.reset`"; the function deletes by `tenant_id` and the outbox must not be a tenant table (the generated isolation and the gap check would need an RLS policy and a row). One extra `DELETE`, listed in `test/policy/no-delete/5c.json`.
4. **The seed takes two new optional dependencies**, `operatorDb` and `prescriptionProvider` (`seed.ts`, `stage2.ts`, `reset.ts`), edits outside the track's own list, additive. Without `operatorDb` the cardiologist cannot be verified (only the operator's role can) and nothing is prescribed. `start-stack.ts` no longer verifies by a raw `UPDATE` after the seed: the seed does it, so a reset keeps it.
5. **The matricula is verified through the real operator function, with the identity of the seed** (`DEMO_OPERATOR`), not an `UPDATE`. It writes the platform trail (`operator.matricula.verified`) and the organization's own (`matricula.verified`) on every seed and reset.
6. **Prescriptions are Valentina's two, Joaquín's one and Martina's one (cancelled), not Santiago's.** The e-prescription browser journey uses patient 99000002 (Santiago) and counts the prescriptions on screen.
7. **`portal_session` keeps its exemption** (a session lives hours and needs a code); the other four portal tables, the consent tables and `prescription` and `erx_connection` are seeded and their exemptions are gone. `action_token` left the core list: the invitations of the portal leave (revoked) links in it.
8. **The demo outbox uses the application role to read.** The console already creates a runtime connection for the e-Rx simulator; the outbox follows it instead of granting the operator role `SELECT` (the operator role is an allowlist).
9. **TDD order for the outbox's adapter.** The adapter was written before its integration test; the test was then written, run (11 passed) and mutation-checked (forwarding in production fails it). The unit test of the policy and the component test were written after and before their code respectively; neither was run red.
10. **A command-line seed runs in another process than the API**, so the provider console does not know the prescriptions it issued (the in-memory fake lives in the API). The stack and the console's reset pass the process's fake (`demoPrescriptionProviderOf(config)`), so there it does.
