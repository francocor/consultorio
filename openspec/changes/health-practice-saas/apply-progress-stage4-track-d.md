- A charge for every billable visit of the last two weeks (about 60 to 80, whatever day it is seeded): pending, partly paid, paid, voided; late fees for no-shows and late cancellations, some flagged.
- Payments of the six methods, a split card voucher with its override reason, an overpayment kept as a credit, three or four refunds, a correction after a close.
- One register per place and day, closed with the count (the 2nd closed one short, the 7th over, with reasons), one open today at each desk of reception. The Córdoba branch is served by the owner as the desk (reception does not work there).

## Findings and deviations

1. **The numbering of simulated vouchers (a bug, fixed).** Seeding invoices through the seed's own fake made the first invoice issued by the running stack's fake (which numbers from its own memory) collide with `invoice_number_key`, leaving it pending. The same happens after a reset of the local simulator. `InvoiceRequest` gained an optional `lastKnownNumber` (the highest voucher number the organization holds for the point of sale and type); the fake and the local simulator number after `max(what they hold, the hint)`; the real authority will ignore it; the hint is left out of the idempotency fingerprint so a retry whose hint moved gets the same voucher. This edits track C code (`ports.ts`, both adapters, `voucher-rules.ts`, `issue-attempt.ts`, the contract suite).
2. **No invoice "flagged as a prolonged outage" in the seed.** The flag is computed from `created_at`, and the trigger `guard_invoice_line_insert` only accepts the lines of an invoice when `invoice.created_at = now()` (the transaction time), so an old pending invoice cannot be written without relaxing an immutability trigger for demo organizations. I did not. The demo shows the flag live (the provider console puts the issuer in an outage), the walkthrough says so, and `afip-issue-job.test.ts` proves it. The "pending, rejected, manual, credit note" part is seeded, with the manual voucher replacing a pending invoice.
3. **Flagged charges are produced by raising the scheduling event** (`flagChargeForReview` with a `status_changed` or `cancelled` event built from the real appointment) for a fee that is still owed: the seed does not go through a real transition (the listener only flags a charge that existed before the visit ended).
4. **`reset.ts` also removes the invoice PDFs and export files** from the bucket (the existing "takes the files out of the bucket" test caught the orphans).
5. **A card number typed in free text is kept.** Only `externalRef` is refused when it looks like a card number. A reason or a description is stored as typed (the audit entry of a void shows its reason). The logs never carry it (tested). Whether free text should be scanned too is a product decision; recorded for the review.
6. **The AFIP mode is global.** `e2e/support/afip-lock.ts` is a directory lock named after the API port; `stage4-invoicing.spec.ts` (track C) and the new journey take it, so two workers cannot put the one fake in conflicting modes. The new journey works in the second organization (`norte`), which no other spec touches.
7. **`test/support/invoicing-world.ts`** got an optional `app` option (a log stream); backwards compatible.
8. **`money-invariants.test.ts` has a database part** that runs in the integration run (`describe.skipIf` without `runtimeUrl`), because `test/policy` is also part of the unit run, which has no database. It shows as one skipped test in `pnpm test`.
9. Web text: `billing.json` has `payers.on`, `payers.off`, `payers.cuit.editShort`, `prices.on`, `prices.off`.
