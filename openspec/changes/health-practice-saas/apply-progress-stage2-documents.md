## What was built

- **Content sniffing (S2.25, task 2.76).** `platform/files/sniff.ts` decides what a file is from its bytes: PDF, JPEG, PNG, WebP, plain text (valid UTF-8, no binary control characters, no script) and DOCX (a ZIP with the Word parts). It refuses executables (MZ, ELF, Mach-O, Java class, WebAssembly), scripts (shebang, PHP, HTML, SVG, `<script>`), archives (ZIP that is not a DOCX, RAR, 7z, gzip, bzip2, xz, zstd, CAB, tar), a DOCX with a macro project, and polyglots: a PDF whose bytes also end like a ZIP, an image with data after its last byte, a DOCX with data after the ZIP directory. `platform/files/test-files.ts` builds small valid files of each type for tests and for the Stage 2 demo.
- **Malware scanner (S2.25, task 2.75).** Port `platform/scanning/malware-scanner.ts` (`ScanVerdict`, `ScannerUnavailableError`), the clamd adapter `adapters/clamav/clamd-client.ts` (`zINSTREAM` over TCP, 64 KB frames, connect, idle and total timeouts, every failure that is not a verdict becomes `ScannerUnavailableError`), and the fake `adapters/fake-scanner` (flags the EICAR string, can be switched off). The test string is written in parts in the source so it does not trip the antivirus of a developer machine. A fake clamd server (`adapters/clamav/fake-clamd-server.ts`) drives the unit tests; a slow suite runs against the real `clamav/clamav:1.5.4-debian` image only with `SLOW_TESTS=1`.
- **Schema (task 2.77).** `db/schema/documents.ts` and migration `0040_documents`: the `document` table with status `quarantined|available|rejected|hidden`, classification and category, sha256, scan result, rejection reason, the replacement link (`replaces_document_id`, unique per live replacement) and the duplicate link, nullable `encounter_id` and `appointment_id`, composite foreign keys to patient and professional, and the CHECK constraints that tie the classification to the category, clinical to an author professional, and `available` to a hash and a detected type. Row level security: `tenant_isolation` plus a RESTRICTIVE policy `document_classification` (administrative rows are visible to the staff; clinical rows only to a professional through `app.clinical_readable`; the system user of the jobs and the owner role pass). `app_rw` cannot delete or truncate. A BEFORE UPDATE trigger fixes the identity of a row, writes the scan results once, moves the storage key only when the scan releases the file, and allows only quarantined to available or rejected, and available to hidden.
- **Upload pipeline (tasks 2.78, 2.79).** `POST /documents/uploads` validates up to 10 files of at most 20 MB and the whitelist of declared types, inserts one quarantine row per file (key `t/{tenant}/quarantine/{id}`, name sanitized and never used in a key) and returns one presigned POST per file that pins the key, the type and the size. `POST /documents/:id/uploaded` is the confirmation: the uploader only, the object must exist, the scan is queued in the same transaction, `document.uploaded` is audited. A replacement (`replacesDocumentId`) must be the next version of an available document of the same patient and classification. A sha256 hint warns about a duplicate before the file is sent. Job `document.scan` (worker): read the object (capped), sniff, compare with the declared type, hash, ask the scanner; clean moves the object to `t/{tenant}/docs/{id}` and the row becomes `available` (a crash between the move and the commit is finished by the retry); infected or not allowed becomes `rejected`, the object is removed and the uploader gets an email with the reason and no file name; a scanner that cannot be reached leaves the document quarantined and queues the job again with a delay of 30 s doubling up to 15 minutes, with an alert (log error and `document_scan_overdue_total`) after one hour.
- **Download and lifecycle (tasks 2.80 to 2.83).** `POST /documents/:id/download-link` and `GET /files/:token`: kind `document_download` is enabled (bound to the session, 5 minutes, single use); the authorization is decided at issue and again at redemption; the API streams the file with `attachment` (ASCII fallback plus `filename*`), `no-store`, `nosniff` and a sandboxing CSP. List (`GET /patients/:id/documents`, latest version only, hidden on request), versions, hide (reason required, file kept), reclassify (professional only). Reception sees the name and category of clinical documents only when the organization allows it, through the definer function `app.reception_clinical_documents`; an administrator never does. `app.document_probe` tells a clinical document the caller may not read (403 and a deny audit entry) from one that does not exist (404). Job `document.cleanup` (hourly per organization): marks uploads never confirmed after 24 hours as abandoned and removes their orphan object, never a row; queues the scan again for a confirmed upload that has been quarantined with no activity for 30 minutes.
- **UI (tasks 2.84, 2.85).** `features/documents`: the "Documentos" tab of the patient record with status chips ("Analizando", "Disponible", "Rechazado", "Oculto"), classification chips, size, uploader and date, download through the link flow, hide with a mandatory reason, versions, and a multi-file upload dialog with category, drag and drop, early refusal of wrong type, size and count in Spanish, per-file progress, a duplicate held for a decision, retry, and a replace mode. The cancellation export contributors (administrative and clinical parts) and `docs/runbooks/documents.md` (the retention note).
