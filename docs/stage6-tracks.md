# Stage 6: what each parallel track may touch

The seam slice (S6.00) registers every shared piece once. After it a track only **adds files** in its own places and **fills in** the placeholders the seam created for it. This page lists, per track, what it owns, what it consumes and exports, and what it must leave alone. If a track needs a change outside its list, that is a new seam commit (ask for it), not an edit made in passing. It follows the layout of `docs/stage5-tracks.md`.

The tracks are A subscriptions (S6.01, S6.03 to S6.06, and the subscription half of S6.07), B signup (S6.02 and the signup half of S6.07), C retention (S6.08 to S6.10) and D readiness (S6.11, S6.12). Run order and dependencies are in `tasks.md`: A (S6.01), B (S6.02, after S6.01 for the trial door) and C (S6.08) start together. C does not wait for billing: cancellation is announced through the `TenantCancelled` door of `modules/tenancy/application/lifecycle.ts`, which S6.04 (subscriptions) and the operator action of task 6.36 both publish to. S6.03 to S6.06 are sequential inside A. S6.07 waits for A and B. S6.11 waits for A and C. S6.12 last.

There are two new ports in Stage 6: `paymentsGateway` (the `PaymentsGateway` of `modules/subscriptions/application/ports.ts`) and `archiveStore` (the `ArchiveStore` of `modules/tenancy/archive/ports.ts`). The seam registered no table and no migration; it enabled one token kind (`cancellation_export`) and left `archive_release` disabled until task 6.41.

## The rules that this stage learned the hard way

Stage 4 (AFIP) and Stage 5 (e-prescription) each needed five rounds of review for the same family of defects: a provider that is not idempotent, a request that is still in flight when the caller gives up, and a connection held while a provider answers. The Mercado Pago port is written for all of it, and every track that touches money or the archive keeps to it.

1. **The key is a courtesy, not a guarantee.** `PaymentsGateway.honoursIdempotencyKey` says whether the provider answers a resend of a key with the same resource. The real Mercado Pago does not for preapprovals: assume `false`. A resend can make a second preapproval, payment link or refund.
2. **Write ahead, ask the provider, adopt carefully, park.** Record the intent (server-derived `externalReference`, the key, the amount, the instant of sending) in a short transaction BEFORE each call, and the answer in another one AFTER. After any outcome that is not known (`retryable` with `outcomeUnknown: true`, a timeout, an abort, a crash after the mark) search by reference (`findPreapprovalsByReference`, `findPaymentLinksByReference`, `findPayments`, `getPayment` for the refunds). Adopt a match only when EVERY identifying field is equal to what you asked for (reference, payer, amount, currency; for a refund: the payment and an amount that was not among its refunds before the call). More than one plausible match, or none that fits, parks the subscription for the operator: never pick one.
3. **A settle window.** `settleWindowMs` is how long a request that the caller gave up on may still land at the provider. Do not believe "nothing was created" and do not send the same write again before that much time has passed since the last attempt. Keep the instant of the last attempt in the row (the pin of `docs/stage5-tracks.md`, `provider_in_flight_until`, is the model; `prescriptions/application/lease.ts` and `settle.ts` show the shape).
4. **Every call is bounded and abortable.** Pass an `AbortSignal` that fires after your own timeout. The fake and the contract suite prove an aborted call never lands unless the provider lets it complete late (`hold({ completeLate: true })`).
5. **No database transaction is open while a method of the port waits.** Not the one `runJob` opens for a handler (it stays idle for the length of the call), not a request's. See "The connection pool" below.
6. **A webhook only enqueues a reconcile.** `verifyWebhook` returns who and what to ask about (`WebhookNotice`: event id, topic, resource id, signed instant), never a status. The route verifies the HMAC and the signed time window (five minutes) over the RAW body, records the event id (`subscription_event`, UNIQUE) and queues `subscription.reconcile`; the state is whatever `getPreapproval` / `getPayment` answer when asked. A duplicate, an old or a forged notice changes nothing.
7. **Transitions come only from provider-confirmed events and dates, never from a missing confirmation.** An outage, a timeout or an unknown outcome never advances the dunning, never cancels, never regresses a state.
8. **The operator never reads content.** The operator views of subscriptions and of the archive carry counts, states and flags, never a patient, a message or a record. The operator role has no clinical table; the routes of the operator in this stage go through `app_operator` and a test proves it.
9. **Every table gets row level security and FORCE.** A `SECURITY DEFINER` function gets a pinned `search_path` ending in `pg_temp`, `REVOKE ... FROM PUBLIC` and an entry in `test/support/function-catalog.ts` / `definer-functions.test.ts`. Never edit an applied migration; a fix is a new one. See "Migration convention" below.

### The connection pool (read this before writing a job)

`runJob` opens a transaction for every handler. A handler that waits for an outside service holds that transaction idle and needs a second connection for its own work; the families that do so are listed in `CONNECTION_HOLDING_JOBS` (`platform/jobs/concurrency.ts`) and set the floor of the pool (`MIN_DB_POOL_MAX`, today 26 after the retention track; the default is 26 and `.env.example` must say `DB_POOL_MAX=26` or more). The Stage 6 families that will wait the same way are named in `PENDING_CONNECTION_HOLDING_JOBS`: `dunning.step` and `subscription.reconcile` (the payments gateway) and `archive.release` (it runs only in the `releaser` process, which has a pool of its own). The retention track moved `export.build`, `archive.write` and `archive.verify` into the list that sets the floor.

They are NOT in the list that sets the floor, because every family added raises it by four connections and the seam may not edit `.env.example`. **The track that writes one of these handlers** writes it with the short-transaction pattern, moves the name from `PENDING_CONNECTION_HOLDING_JOBS` to `CONNECTION_HOLDING_JOBS`, raises `DEFAULT_RUNTIME_POOL_MAX` (`platform/db/pool.ts`) to the new floor or more, and asks the maintainer for the `DB_POOL_MAX` line of `.env.example` (the file of the maintainer: `config.test.ts` loads it as it is and fails below the floor), then updates `docs/runbooks/deploy.md`, `config.test.ts` and the pool paragraph of `docs/security/asvs-l2-portal.md`. Do not raise the floor without that, or the example configuration stops starting. `concurrency.test.ts` keeps the two lists apart and complete.

## Rules for everyone

1. Run `pnpm db:restamp` and `pnpm db:check` after every merge or rebase that touches the journal.
2. Add a locale file for every screen text; no literal text in JSX (lint). The empty `errors.<module>.json` are yours to fill with the message of each code.
3. A web feature imports another feature only through its `index.ts` (lint). The wizard and the invitation dialog reach the subscription pieces through `features/subscription/index.ts`.
4. Cross-module calls on the API go through `modules/<other>/index.ts` and through the lifecycle and appointment events. The operator routes of a module are registered by its own wiring (`operatorRoutes`).
5. Every mutating route declares `config.audits`, every route a read-only category, every job its queue category.
6. No card data is ever stored, logged or put in audit metadata; the owner sees only the label the provider gives. The content of an archive, a message or a clinical record is never in an operator response.
7. A download is never a new route: register a `FileResource` in the right registry (staff `fileResources`, portal `portalFileResources`) and let the door serve it.
8. Anything a simulator produces says so: the boot flag `localProviders.payments` on the screens (a `SimulatedPaymentsNotice` like `app/SimulatedBillingNotice.tsx` shows when it is true), and the hosted checkout page says "simulated" in es-AR.
9. A provider call is bounded, abortable, preceded by a write-ahead mark and never inside a transaction (the rules at the top).

## Gotchas

- **Stale globs in the unit runner.** Feature registries (`routes.tsx`, `nav.ts`, `slots.tsx`), locale files, fixtures and demo exemptions are found with `import.meta.glob`. Vitest caches the transform of the file that holds the glob, so a test can miss a file you just added. Remove `node_modules/.vitest-cache` (and re-run) after adding one.
- **`TenantCancelled` and `featureRoutes` are new mechanisms.** `ModuleWiring.create()` may return `featureRoutes`; a route that belongs to the platform (signup, subscriptions) goes there, so single mode never serves it. A module that needs to publish or subscribe to the end of an organization uses `context.tenantLifecycle`; it does not call another module.
- **The queue `dunning.step` never retries on its own** (`retryLimit: 0`). Do not "fix" that to match the others.
- **`createTrialStarter()` refuses today.** The wiring of the signup compiles and boots; a verified signup before S6.01 lands fails on purpose and rolls back.
- **Under load a handful of unit files can time out** that pass alone: re-run them alone before suspecting the code.
- **`.env.example` is the maintainer's file**: the seam may not edit it. Anything that needs a new line there (the pool floor, the archive variables, the Mercado Pago ones) is a request to the maintainer, listed in the track's progress file.
