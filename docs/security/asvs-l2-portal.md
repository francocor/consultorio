# ASVS Level 2: patient portal checklist

Scope: the patient portal delivered in Stage 5 (sign-in with an emailed code, sessions, own-data-only access, the signing of consents, the prescriptions and documents a patient downloads, the staff side that invites and links) and the two modules it reads through their public entry points (consent and e-prescription), measured against OWASP ASVS 4.0.3 Level 2. What was already claimed for the staff side in Stage 1 is in `asvs-l2-stage1.md` and is not repeated; where the portal reuses a control of that page it says so.

How to read it: **Met** has a test or a file you can open; **Partial** says what is missing; **Accepted** is a decision recorded with its reason; **Later** is out of scope for this stage. Paths are relative to the repository root. A test named in a row is one that fails if the control is removed; the rows were checked by running the suite, not by reading the names.

Review status: this page was written by the author of the integration slice (S5.13, task 5.51) from the code and the tests. The fresh-context review (`judgment-day`) of portal isolation, consent integrity and prescription access is the second half of the task; it is run by the orchestrator and its report is attached to the apply-progress of Stage 5, not written here. The probes it starts from are in `apps/api/test/security/stage5-isolation.test.ts`.

## V2 Authentication

| Requirement                                                    | Status   | Evidence                                                                                                                                                                                                                                                                                                                                                            |
| -------------------------------------------------------------- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 2.1 Passwords                                                  | Met      | The portal has no password: a patient signs in with a code sent to the verified address, so there is nothing to reuse, guess or breach-check                                                                                                                                                                                                                        |
| 2.2.1 Anti-automation of credential attacks                    | Met      | Six digits, ten minutes, five wrong attempts, three sends per address per hour, and a lock after ten tries per address that applies to unknown addresses alike (`modules/portal/domain/code.ts`); `portal-signin.test.ts`: "spends the code on its fifth wrong attempt", "stops answering for an address after too many tries", "sends at most three codes an hour" |
| 2.2.2 Account enumeration                                      | Met      | The same answer for an account, an unknown address and a deactivated one, and the same for a registration with a wrong document or address (`portal-signin.test.ts`: "answers the same for an account, an unknown address and a deactivated one", "is wrong with another document, another email, a wrong code or no code, always the same way")                    |
| 2.2.3 Notify on security-relevant changes                      | Met      | A change of the address of an account ends its sessions and is audited (`portal.profile.changed`); the notices of the portal say that something waits, never what (`test/policy/portal-message-privacy.test.ts`)                                                                                                                                                    |
| 2.3.1 System-generated initial secrets, single use, expiring   | Met      | The activation link is a single-use token valid seven days (`platform/tokens/kinds.ts`, `portal_activation`); a second press and a link that was only opened find nothing to do (`portal-identity.test.ts`: "works once", "refuses a link that expired"); a newer link replaces the older one                                                                       |
| 2.5 Credential recovery                                        | Met      | There is nothing to recover: a lost phone is a new code to the same address; a deactivated account cannot ask for one and a code asked for before the deactivation does not sign in (`portal-signin.test.ts`: "a code for a deactivated account")                                                                                                                   |
| 2.7.1 Out-of-band verifiers: code length, lifetime, single use | Met      | Six random digits (`crypto.randomInt`), ten minutes, spent on use, one live code per account (the newest replaces the older); stored as a hash tied to the challenge (`hashCode`), compared in constant time (`codeMatches`); `portal-signin.test.ts`: "keeps one live code per account", "refuses a code after its ten minutes"                                    |
| 2.7.2 Out-of-band verifier is not guessable beyond its life    | Accepted | A six digit code is small enough to be searched: the protection is its ten minute life, five attempts and the per-address lock above, not the hash (`code.ts`, comment). It is the same rule as the public booking codes                                                                                                                                            |
| 2.9 Cryptographic verifiers                                    | Later    | Not used: no device-bound or hardware credential in this stage                                                                                                                                                                                                                                                                                                      |
| 2.10 Service authentication                                    | Met      | The e-prescription provider's notice is signed with `ERX_WEBHOOK_SECRET` and checked before anything else (`modules/prescriptions/http/webhook-routes.ts`); the demo and the local simulator use a secret per process when none is set, never a default                                                                                                             |

## Findings carried to the review

Things the author of this page could not close alone, for the fresh-context review to look at first:

1. **Six digit codes (2.7.2).** Accepted on the grounds above. The reviewer should confirm that the per-address lock and the per-IP limits of `/public/:slug/portal/*` keep a distributed guess below a useful rate.
2. **The demo outbox.** It holds the text of the emails a demo organization "sent", including sign-in codes. It is written only for demo organizations, read only behind the operator session on the platform host, and exists only where the provider console is on (always in development, and in production only with `ALLOW_LOCAL_PROVIDERS=true`). The reviewer should confirm that no route reads it for a customer organization.
3. **Seeded accounts.** The demonstration organization has portal accounts at fictitious `.invalid` addresses; a code can only be read from the outbox. The reviewer should confirm that the seed never runs in production with the public password (`db/seed/demo/seed.ts` refuses it).
4. **Documents rendered on request.** The portal says a prescription has a document when one can be made; if rendering fails (storage down) the download answers 404 and the button says so. This is an availability matter, not an access one.
