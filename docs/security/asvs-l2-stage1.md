# ASVS Level 2: Stage 1 checklist

Scope: the secure core delivered in Stage 1 (organizations, identity, staff, patients, anamnesis, audit, branding, operator console, demo organization) measured against OWASP ASVS 4.0.3 Level 2. Anything that belongs to a later stage (patient portal, online booking, payments, e-prescriptions, uploads of clinical documents) is marked **Later** and is not claimed.

How to read it: **Met** has a test or a file you can open; **Partial** says what is missing; **Accepted** is a decision recorded with its reason; **Later** is out of scope for this stage. Paths are relative to the repository root.

Reviewed on 2026-10-16 by one author in a separate pass over the code after implementing it, and then by a fresh-context security review of the backend that found ten more things; all of them are handled (see "Independent security review"). Findings of the first pass and what was done with each are in "Review findings".

## Independent security review

A fresh-context review of the Stage 1 backend (`main..ef72fed`) found ten things. Every one is fixed or already satisfied; each fix has a failing test written first and is a commit of its own.

| #   | Finding                                                                                             | Severity | Resolution                                                                                                                                                                                                                                                                                                     |
| --- | --------------------------------------------------------------------------------------------------- | -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | Host-header poisoning of reset and invitation links                                                 | High     | Fixed: links come from configuration (`{slug}.BASE_DOMAIN` in multi mode, the required `PUBLIC_URL` in single mode), never from the request (`platform/http/public-origin.ts`, `test/integration/link-origin.test.ts`)                                                                                         |
| 2   | `X-Forwarded-For` spoofing with `TRUST_PROXY=true`, and a non-IP value turning into a 500           | Medium   | Fixed: `TRUST_PROXY` is a hop count (default 1 in production) or a list of proxies, `true` is refused; a non-IP address is audited as unknown (`main/trust-proxy.ts`, `request-context.test.ts`, `test/integration/client-address.test.ts`)                                                                    |
| 3   | An admin could create a second, clinical account (invite a professional, assign patients to it)     | Medium   | Fixed with decision D19 (pending owner confirmation): only the owner brings professionals in; assignments by non-clinical staff to a professional added in the last 7 days write `assignment.review_flag` (`roles.test.ts`, `access-grants.test.ts`, `staff-lifecycle.test.ts`, `care-assignment-api.test.ts`) |
| 4   | SECURITY DEFINER functions executable by PUBLIC                                                     | Medium   | Fixed by migration 0019: explicit grants, a search path pinned first to `pg_catalog`, new functions closed by default, and a catalog test that lists every definer function with the only roles that may run it (`test/integration/definer-functions.test.ts`). `app.demo_reset` already followed the rule     |
| 5   | Audit integrity not enforced in the database                                                        | Medium   | Fixed by migration 0020: a trigger refuses a pre-filled seal on both trails, and `audit_sealer` is a login only the worker holds (`AUDIT_SEALER_DATABASE_URL`); neither `app_rw` nor `app_operator` can switch to it (`test/integration/audit-integrity.test.ts`)                                              |
| 6   | Data key cached before its transaction committed                                                    | Low      | Fixed: a key generated by a transaction lives with it, and the shared cache learns it from the database (`test/integration/tenant-keys.test.ts`)                                                                                                                                                               |
| 7   | Operator console: timing oracle on a locked account, `professional` readable, `tenant_key` writable | Low      | Fixed: a locked account pays one Argon2 verification; migration 0021 limits `tenant_key` INSERT to version 1 of an unclaimed organization and `professional` SELECT to the columns of the registration (`operator-auth.test.ts`, `operator-privileges.test.ts`)                                                |
| 8   | An unknown subdomain cost a database lookup before any rate limit                                   | Low      | Fixed: a per-client allowance (four times the per-tenant one, across all hosts) runs before the host guard (`rate-limit.test.ts`)                                                                                                                                                                              |
| 9   | Compose defaults                                                                                    | Low      | Fixed: a loud development-only header and a test that pins it; the API still refuses the local key and insecure cookies in production (`main/compose.test.ts`)                                                                                                                                                 |
| 10  | Missing security headers                                                                            | Low      | Already in place when the review reached them (S1.36): `nosniff`, `DENY`, `no-referrer`, a deny-all CSP and HSTS where cookies are secure (`security-headers.test.ts`)                                                                                                                                         |

Also closed from the first pass: the `__Host-` cookie prefix (3.4.4), the idle timeout (3.3.2) and the Content Security Policy of the web bundle (14.4.7).

Residual risks, stated plainly:

- `TRUST_PROXY` as a hop count assumes the API is reachable ONLY through its proxy and that the proxy appends the address it received the connection from. A deployment that exposes the API port directly lets a client choose its own address.
- The platform operator can still read the registration (number and jurisdiction) of every professional without a support grant: verifying a matricula is the operator's job (D1). The rest of the profile is no longer readable.
- The worker holds two database logins (`app_rw` and `audit_sealer`). Compromising the worker compromises both; compromising the API does not reach the sealer.
- D19 closes the admin path to a second clinical account. The owner can still create one, which is bounded by the owner already controlling the organization.

## Open items before the first production customer

1. Send an email to the person when their password or second factor changes (ASVS 2.2.3), together with the notifications module.
2. Give the scheduled demo reset (job) an operator-role connection in the worker, and decide how a deployed demo hands its rotated passwords to the people who need them.
3. Provision the `audit_sealer` login in the deployment with a managed secret, and make the proxy send `dist/content-security-policy.txt` as the `Content-Security-Policy` header.
4. The owner confirms or amends decision D19.

## Limits of this review

The first pass was written by the author who implemented the stage, after the fact. The second was a fresh-context review of the backend only; it did not cover the web bundle in depth, and neither is a penetration test or a third-party audit. Nothing was verified in CI. The deployment items above are not claimed.
