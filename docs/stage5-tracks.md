# Stage 5: what each parallel track may touch

The seam slice (S5.00) registers every shared piece once. After it a track only **adds files** in its own places and **fills in** the placeholders the seam created for it. This page lists, per track, what it owns, what it consumes and exports, and what it must leave alone. If a track needs a change outside its list, that is a new seam commit (ask for it), not an edit made in passing. It follows the layout of `docs/stage4-tracks.md`.

The tracks are A1 matricula verification (S5.01), A2 consent (S5.02, S5.03, S5.11), A3 e-prescription (S5.04, S5.05), B portal (S5.06 to S5.10) and C integration (S5.12, S5.13). Run order and dependencies are in `tasks.md`: A1, A2 (S5.02), A3 (S5.04) and B (S5.06, S5.07) start together. The e-Rx gate reads the existing `matricula_status` column, so S5.04 does not wait for S5.01 (only its end-to-end test does). S5.08 waits for S5.03, S5.04 and S4.12. S5.11 waits for S5.03 and S5.10. C starts when everything else is merged.

There is one new port in Stage 5: `prescriptionProvider` (the `PrescriptionProvider` of `packages/contracts/src/ports.ts`). The seam registered no table, no migration, no settings section and no token kind: the portal uses `portal_activation` and `document_download`, which already exist and are enabled.

## Rules for everyone

1. Run `pnpm db:restamp` and `pnpm db:check` after every merge or rebase that touches the journal.
2. Add a locale file for every screen text; no literal text in JSX (lint). The empty `errors.<module>.json` are yours to fill with the message of each code.
3. A web feature imports another feature only through its `index.ts` (lint). The portal reuses the consent signing components through `features/consent/index.ts`.
4. Cross-module calls on the API go through `modules/<other>/index.ts` and through the appointment events. The portal never reads another module's table.
5. Every mutating route declares `config.audits`, every route a read-only category, every job its queue category.
6. A prescription's items, a consent's text and signature evidence, and a portal code or token are never logged, never in audit metadata and never in a notification.
7. A download is never a new route: register a `FileResource` in the right registry (staff `fileResources`, portal `portalFileResources`) and let the door serve it.
8. Anything a simulator produces says so: the boot flag `localProviders.erx` on the screens, the `watermark` option of `renderPdf` on the document.

## Gotchas

- **Stale globs in the unit runner.** Feature registries (`routes.tsx`, `nav.ts`, `slots.tsx`), locale files, fixtures and demo exemptions are found with `import.meta.glob`. Vitest caches the transform of the file that holds the glob, so a test can miss a file you just added. Remove `node_modules/.vitest-cache` (and re-run) after adding one.
- **The old `kind: 'patient'` actor** (`Actor`) is kept only so staff routes keep denying it; the portal uses `PortalActor`. Do not build new code on the old kind.
- **No settings section, token kind, queue, permission or audit action is left for a track to add.** If you find one missing, it is a seam commit.
- **The Stage 4 fixes are merged into Stage 5 later.** Expect conflicts only in the journal (`pnpm db:restamp`, keep every entry), `apply-progress.md` (keep both sections) and, if the fixes touch them, `main/wiring/types.ts` and `platform/files/file-resources.ts`.
- **Under load a handful of unit files can time out** that pass alone: re-run them alone before suspecting the code.
