# ADR: the calendar is our own grid, behind a swappable component

- Status: accepted (Stage 2, S2.12)
- Settles: design question **Q6** ("is react-big-calendar polished enough for the portfolio-flagship bar, or do we budget a custom grid?")
- Where: `apps/web/src/shared/ui/calendar/`

## Decision

`CalendarView` is a purpose-built grid (CSS grid, no calendar library). Its API is presentational and knows nothing about appointments: it takes `resources`, `events`, `backgrounds` and `closedDays`, and reports `onSelectEvent`, `onSelectSlot`, `onMoveEvent` and `onSelectDay`. A screen maps its data to those shapes (`features/calendar/domain/calendar-events.ts`). If the grid is ever replaced, no screen changes: that is the "swappable behind our own API" requirement of the design, kept.

## What was evaluated

react-big-calendar 1.20.0 (MIT) was installed in a scratch folder (outside the repository), rendered with a day, week and month view with two resource columns, a luxon localizer and React 19, and checked in jsdom with axe (the same engine as our component tests). Findings, each measured or read from the package:

| ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |

| axe, week view               | **2 critical violations** (2 and 16 nodes)                                                                                                                                                                                                                                               | none                                                                                                                                                 |
| axe, month view              | none                                                                                                                                                                                                                                                                                     | none                                                                                                                                                 |
| Time zone of the location    | Works on JS `Date`s in the **device** zone. A location zone needs a process-wide default (`luxon` `Settings.defaultZone`) or shifted fake dates. The spec says an appointment is shown at the location's time, whatever the device says, and DST gaps/overlaps are explicit requirements | Every conversion goes through `Intl` with the location's zone (`zoned-time.ts`); a DST test pins a 23-hour day                                       |
| Locale                       | The localizer renders `10:00 a. m. – 10:30 a. m.`; the product uses a 24-hour clock                                                                                                                                                                                                      | `HH:mm` everywhere                                                                                                                                   |

Week view: a column per day, the professional named on each appointment                                         |

Where react-big-calendar is better: it is mature, its month view passes axe, and it would have saved the overlap layout. None of that outweighs the failures above, which are exactly the product bar of this screen (accurate time zone, keyboard access, WCAG on the day and week views that reception uses all day).

## Consequences

- We own about 700 lines of grid code and their tests. The risky parts are pure and exhaustively tested: `zoned-time.ts` (zone and DST arithmetic), `calendar-layout.ts` (overlap lanes, snapping, pointer-to-time).
- Dragging uses pointer events for a mouse or a pen. Touch keeps scrolling; a phone moves an appointment from its drawer ("Reprogramar"). The keyboard has `Alt` + arrows.
- **Resizing is not offered.** The end of an appointment is derived from its type's duration (scheduling spec, "Booking an appointment"), and the API has no way to set it. Dragging an edge would promise something the system cannot do.
- A location with its own zone draws the calendar in that zone; with several zones and no location chosen, the first active location's zone is used (`resolveTimeZone`). Appointments are absolute instants, so this only changes how they are labelled.
- If a future need (recurring-event editing, a timeline view) tips the balance, replace the internals of `CalendarView`; the screens and their tests are written against the presentational API.
